# V1 Operational Finance Implementation Plan

Status: implementation in progress

Branch: `v1/integration`

Planning baseline: `c934851ed658ae209ce1fab902a7866718365d60`

This plan implements the owner-authorized transition from the narrow E1 finance sandbox to daily
operational finance. It is additive. It preserves the established identity, Treasury, Finance,
General Ledger, exchange-rate, reversal, audit and least-privilege boundaries. Earlier delivery
documents that deliberately deferred Sales, Procurement and Payroll describe the previous scope;
the owner's operational-finance order explicitly authorizes the slices listed here.

The implementation rule is **one business event, one authoritative source record, all downstream
accounting effects generated by the secured posting boundary**. Posted records are never silently
rewritten. Money uses fixed-precision decimal values. Original currency, base currency and the
historical exchange-rate snapshot remain explicit. Amounts in different currencies are not added
without a named conversion basis.

## A. Existing functionality reused

- Database-backed employee identity, sessions, roles, permission catalogue and legal-entity scope.
- Type A users, Type B business parties and Type C ledger accounts remain separate.
- Business-party roles already cover shareholder, customer, supplier, contractor, employee and
  saraf classifications.
- Legal entities, projects, departments and cost centres supply accounting dimensions.
- Configured currencies, exact decimal conventions, exchange rates and immutable rate snapshots.
- Governed Chart of Accounts with asset, liability, equity, revenue and expense classifications.
- Accounting calendar and open-period validation.
- Shareholder agreements, instalments and capital-intent provenance.
- Treasury cash locations, per-currency accounts, cashier assignments, counts, receipts and
  Treasury-to-Finance handoff.
- Restricted Finance posting intents, balanced journals, journal lines, sub-ledger entries,
  idempotency, evidence bindings, audit records and outbox events.
- Controlled journal reversal requests and posted General Ledger activity/read projections.
- The existing restricted runtime pattern: server-issued session token, database authorization,
  narrow `SECURITY DEFINER` entry point, non-login least-privilege owner and explicit grants.

## B. Existing functionality that needs extension

1. **Permission catalogue and navigation**
   - Add operation-specific permissions for workflow configuration, daily operations, parties,
     expenses, income, customer receipts, supplier purchasing/payment, salary/wage payment,
     transaction register and reporting.
   - Keep administration permissions independent from financial operating permissions.
   - Replace preview/design navigation with a permission-derived operational Finance navigation.

2. **Business parties**
   - Add governed operational party registration and role assignment instead of duplicate
     shareholder/customer/supplier/employee masters.
   - Add role-specific profile fields only when the business process needs them.

3. **Treasury and posting**
   - Generalize source bindings through typed source records rather than weakening the existing
     shareholder-capital functions.
   - Add outbound disbursement and transfer sources with linked, balanced accounting effects.
   - Derive balances from finalized transactions/journals; do not store editable totals.

4. **Finance read models**
   - Add source drill-down, transaction register, party statements, daily movement and
     per-currency treasury positions while preserving entity/project/cost-centre scope.

5. **Reversals**
   - Link operational source records to the existing controlled journal reversal process and add
     source status/history updates after a posted reversal.

## C. Genuinely missing capability

- Company-level approval policy by workflow type.
- Operational daily expense and other-income source records.
- Customer profiles, sales contracts, instalment obligations, receipts and receipt allocation.
- Supplier profiles, material master, purchases, payables and payable settlement.
- Controlled salary/wage payment source records without recreating payroll calculation.
- One-operation Treasury transfers.
- Unified finance transaction register and reconciling daily financial report.
- Permission-aware bilingual operational pages for these workflows.

## D. Database migrations

Migrations are incremental and are tested both from an empty database and as upgrades from the
current migration catalogue.

1. `0025_v1_operational_finance_configuration.sql`
   - finance workflow types and per-legal-entity approval policies;
   - financial posting profiles/account mappings that must be explicitly configured;
   - operation-specific permission catalogue entries;
   - narrow configuration and read entry points;
   - Al-Beruniy policy rows with approvals disabled, applied by explicit legal-entity identity and
     never as a universal default.
2. `0026_v1_operational_parties_expenses.sql`
   - governed party profiles, expense categories, expense sources and immutable history;
   - idempotent finalize path, approval-on pending path and approval-off posting path;
   - exact currency/rate snapshot and Treasury/GL source binding.
3. `0027_v1_finance_register_daily_report.sql`
   - scoped transaction projection, per-currency treasury movement and daily report entry points.
4. Later vertical-slice migrations add customer AR, income, supplier/AP/material purchases,
   salary/wage payments and Treasury transfers. Each owns its source data and exposes only narrow
   commands/read models.

No migration seeds fake shareholders, customers, suppliers, expenses or transactions.

## E. API routes

- `GET/PUT /api/v1/admin/finance-workflows`
- `GET/POST /api/v1/finance/parties`
- `GET/POST /api/v1/finance/expenses`
- `GET/POST /api/v1/finance/income`
- `GET /api/v1/finance/transactions`
- `GET /api/v1/finance/reports/daily`
- Customer: `/api/v1/customers`, `/contracts`, `/installments`, `/receipts`
- Supplier: `/api/v1/suppliers`, `/purchases`, `/payables`, `/payments`
- Salary/wage: `/api/v1/finance/compensation-payments`
- Treasury: `/api/v1/treasury/transfers`

Every route obtains the bearer session server-side, uses its dedicated restricted database
credential, validates the response contract and returns stable business-safe error messages.

## F. UI routes and reusable components

- `/finance/today` — role-filtered daily operating summary and quick actions.
- `/finance/expenses` and `/finance/income` — plain bilingual entry forms and registers.
- `/finance/transactions` — unified filterable register with source and journal drill-down.
- `/finance/reports/daily` — selected-date report with per-currency totals and Treasury breakdown.
- `/finance/customers`, `/finance/suppliers`, `/finance/purchases`,
  `/finance/compensation-payments` and `/finance/transfers` in later slices.
- `/admin/finance-workflows` — System Administrator policy/configuration screen.

Shared form components use decimal strings, accessible labels/errors, keyboard navigation, Dari/RTL
layout and permission-aware actions. Technical state-machine codes remain out of normal business UI.

## G. Permissions

Planned catalogue additions are intentionally granular:

- `admin.finance-workflow.manage`
- `finance.party.read`, `finance.party.manage`
- `finance.expense.read`, `finance.expense.record`
- `finance.income.read`, `finance.income.record`
- `finance.customer.read`, `finance.customer-receipt.record`
- `finance.supplier.read`, `finance.purchase.record`, `finance.supplier-payment.record`
- `finance.compensation-payment.record`
- `treasury.transfer.record`
- `finance.transaction.read`, `finance.daily-report.read`

`System Administrator` can configure workflows but receives no Finance permission implicitly.
Finance permissions remain assignable in subsets through the existing role system. Approval-enabled
workflows retain independent submit/approve permissions and segregation rules. Approval disabled is
an explicit company policy decision, not a bypass of authentication, authorization, validation,
posting balance, idempotency, immutability or audit controls.

## H. Tests

Each slice adds:

- contract/parser tests for decimal, currency, dates and typed identifiers;
- domain tests for state transitions, policy choice and accounting construction;
- real PostgreSQL tests for permission, legal-entity/project/cost-centre isolation, direct-table and
  direct-function attacks, idempotency, concurrency, immutable history and upgrade migrations;
- reconciliation tests tying source, Treasury movement, posting intent, journal and reports;
- route tests for authentication, error mapping and response validation;
- serial browser tests for authorized/unauthorized navigation, English/Dari, RTL, keyboard use and
  desktop/tablet layouts.

The required accounting cases are: approval OFF finalizes; approval ON remains pending; expenses
reduce the selected Treasury account; income increases it; customer receipts reduce receivables;
shareholder capital retains its existing trace; credit purchases create AP without cash movement;
supplier payments reduce AP and Treasury; FX snapshots are immutable; reversals preserve originals;
daily reports reconcile; and two companies may use different policies.

## Delivery sequence

1. Approval policy configuration and permission catalogue.
2. Permission-derived operational navigation.
3. Daily expense from source entry through Treasury/GL posting.
4. Unified transaction register and daily report.
5. Operational party register and shareholder account improvements.
6. Customer contract, instalment and receipt vertical slice.
7. Other income.
8. Supplier account and material purchase/payable/payment vertical slice.
9. Salary/wage payment.
10. Treasury transfer and final cross-module reconciliation.

An operation does not become available merely because its screen exists. It remains fail-closed
until its company workflow policy, ledger posting profile, currency/rate rule, open period and user
permission are all valid. Unresolved accounting policy is surfaced as required configuration, never
invented in code.
