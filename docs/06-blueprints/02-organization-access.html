THE ACCESS MODEL — six distinct objects, never merged
1USER ACCOUNTIdentity for authN. MFA. One person = one login. Employee / portal user.
2ROLEJob function bundle of permissions. A user may hold several.
3DEPARTMENTHome org unit. A user belongs to exactly one department.
4PROJECT ASSIGNMENTScopes which projects' data a user may touch. Many per user.
5PERMISSIONAtomic can-do (create/read/update/approve on an object).
6APPROVAL AUTHORITYAmount/scope limits per user per project. Feeds Workflow. WF-01
Effective Data Access = Role Permissions ∩ Project Assignments ∩ Department scope ∩ Field-level rules. Computed at every request by the Permission Engine. SEC-01

AUTHORITY & DATA-ACCESS EXAMPLES — same object, different power by role & project
Finance Manager
Approves expenses/payments ≤ threshold T1; posts JEs; sees all-project finance in own entity.
CFO
Approves > T1 up to T2; above T2 escalates to CEO/Chairman. Company-wide finance view.
Project Manager
Full ops on assigned projects only; cannot see other projects or payroll.
Chairman
Read-all every project + consolidation; approves top-tier limits; no data entry.
Sales Agent
Sees own customers & assigned unit inventory; no payroll, no company finance.
Warehouse Officer
Creates stock in/out/transfer; cannot approve payments or view AP ledger.
Collection Officer
Views assigned overdue customers; records receipts; cannot waive penalty (needs FM).
Procurement Officer
Raises RFQ/PO drafts; cannot self-approve; PO approval by Proc Mgr / Finance.
HR Officer
Employee records & attendance; payroll run requires HR Mgr + Finance approval.
Auditor
Read-only everything incl. audit trail; no create/update/approve.
